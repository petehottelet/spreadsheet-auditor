## Notes by rule

- **BLANK_PRECEDENT**: Almost always noise on real workbooks: formulas that test the cell for blank (="", ISBLANK, comparisons, IFERROR), template rows whose inputs are all blank, mirror links, and MIN/MAX/SUM arguments that ignore blanks. The one true positive was a blank lookup key silently matching blank rows. The rule needs to fire only on an arithmetic or lookup use of a lone blank among otherwise populated inputs.
- **BROKEN_REFERENCE**: Every sampled finding was factually right: 8 genuine #REF! cells and 17 external links. The links are the problem in practice: they are reported once per cell under a 'broken' rule at High severity although they work. They should be one Info-level finding per external source per sheet.
- **CIRCULAR_REFERENCE**: 23 of 25 were positional idioms: ROWS(A$6:A8), COLUMNS($D7:AA7), ROW(A19), COLUMNS($D:Y) where the range ends at the formula's own cell. These functions read position, not value, so they are not dependencies. The two true positives were a deliberate IFERROR(1/(1/F8)) self-reference that needs iterative calculation. Excluding ROW/ROWS/COLUMN/COLUMNS/ISREF/AREAS arguments from the graph removes every false positive here.
- **DUPLICATE_KEY**: The index treats every column inside any lookup-family range as a key column, so SUMIFS criteria columns, VLOOKUP result columns, and category columns are all reported. The true positives were duplicate MATCH keys (postcodes) and duplicate product names in lists searched by name. Only the key column of first-match lookups (VLOOKUP/HLOOKUP first column, MATCH/XMATCH/XLOOKUP/LOOKUP lookup array) should count.
- **FORMULA_DRIFT**: No true positives in this corpus. The failures share three shapes: rows of unrelated formulas where two columns happen to share a pattern and the third differs (three-cell row segments), the seed cell of a chain (year 0 of a projection, the first row of a running balance), and label or derived columns beside mirror columns. Requiring at least four cells in a segment and exempting a chain seed removes most of them; genuine drift in long projection rows is unaffected.
- **HARDCODE_IN_FORMULA_BLOCK**: Two true positives (a literal typed over an IF formula in a formula column). Every false positive is an input column or input row that happens to sit between two formula lines sharing a pattern (running sums, unit x quantity). A plug is isolated: when the cells on the other axis are numbers too, it is an input, not a plug.
- **HIDDEN_STRUCTURE_IN_TOTAL**: Solid where it fires: hidden rows still counted by SUMIFS, hidden helper columns feeding scores, hidden rows inside lookup tables. The false positives are AGGREGATE(...,3,...) totals, which ignore hidden rows by definition, as do SUBTOTAL(101..111). One finding per hidden row also piles up on sheets with many hidden rows; grouping per sheet would read better.
- **IFERROR_MASK**: Disclosure rule; judged TP when the fallback silently replaces a computational error with a number or text that feeds other cells (schedules zeroed by a blank input, ratios showing 0 for no data, a hidden #REF!, IFNA(...,0) on an input sheet), FP for the lookup-miss-to-blank idiom, end-of-list array extraction, and wrappers around functions that cannot error. Also reported once per cell, so one schedule contributes hundreds of findings; one finding per formula block would read better.
- **LITERAL_CONSTANT**: True positives are thresholds and planning assumptions: 37.5 hours, 85-point bands, 90-day bad-debt cutoff, pallet tiers, WORKDAY lead times, '+9' beside an input cell holding 10. False positives are unit and format constants: 60/3600, 3 months, CHAR(10), the REPT(" ",99) split idiom, TIME(23,59,59), WEEKDAY/WEEKNUM type codes, VLOOKUP column indexes, calendar offsets. Skipping literals in known function slots (column index, type code, length, format) and unit conversions would roughly double precision.
- **LIVE_ERROR**: Every sampled finding was a real error value: #REF! formulas, lookups missing their keys, #VALUE! from external links or text arithmetic, and error constants pasted into data. The judgement call is template rows and end-of-list #N/A, which the author expects but every reader sees; labelled TP because the sheet does display errors. Grouping by root cause already keeps the volume sane.
- **MERGED_CELL_IN_DATA_RANGE**: No true positives. Every merge was a title, section header, month header, label beside a price, a totals-row cell, or a merged date whose formulas already fetch the last non-blank value. The rule needs to require the merge to sit inside the numeric body of the read range (not in the header band above the first numeric row) and, for row-spanning merges, that the reading formula keys on that column without a last-non-blank idiom.
- **NUMBERS_STORED_AS_TEXT**: Two variants with opposite precision: 'text number in an otherwise numeric column' was right every time (10/10); 'referenced by a formula' was wrong every time (0/15), firing on leading-zero serials, order numbers and month strings that DATE() coerces. Drop the referenced-by variant unless the referencing formula does arithmetic or aggregation, and never flag values with leading zeros.
- **RANGE_EXCLUSION**: The four true positives were a total whose siblings span all rows while it stops early. The three false positives were a running COUNT($A$9:A9) read as a horizontal range with column B 'between it and the total'. Single-cell and mixed-anchor expanding ranges should be exempt.
- **RANGE_INCLUDES_SUBTOTAL**: All three were a carried-forward total ('this week' + 'last week's total' = 'total overall'); the included column holds constants, which the rule itself reports. Requiring the included column to hold formulas aggregating cells inside the same range would remove these.
- **RANGE_LENGTH_MISMATCH**: True positives were COUNT(D87:F89) in a column of COUNT(D87:F87) formulas: a real fill error. False positives were one-cell SUM(G213:G213) links and debit/credit sums over disjoint column groups. Exempt one-cell aggregates and peers whose ranges do not overlap.
- **VOLATILE_FUNCTION**: RAND/RANDBETWEEN feeding analyses and INDIRECT-built addresses are worth flagging; TODAY() in an age or overdue calculation is not. The one interesting TODAY() case builds the year of a parsed date from today's date, which breaks every January. Treat TODAY/NOW as Info and report once per workbook; keep RAND*/INDIRECT/OFFSET per block.
- **WHITESPACE_KEY**: Two true positives (one padded name among clean names). Everything else was uniform fixed-width padding from an export, indentation, spacer cells, or headers. Skip the header row, skip columns where most text values carry the same padding (one note per column instead), skip leading-space indentation, and keep only the minority-padded value whose trimmed form matches other cells.
- **WHOLE_COLUMN_REFERENCE**: COUNTIFS/SUMIF/VLOOKUP/XLOOKUP/MATCH over whole columns are bounded to the used range and were all false positives. The true positives were array evaluations over whole columns (MAX(IF(F:F=A279,G:G)), LOOKUP(2,1/(J:J<>""))) repeated in hundreds of cells. Flag only array contexts: CSE/dynamic-array formulas, SUMPRODUCT, arithmetic or comparison on a whole column, FILTER.

## Method and caveats

- Every workbook is audited with the CLI in a subprocess with a per-file timeout; crashes and timeouts are counted, not hidden.
- The sample takes up to 25 findings per rule, at most 2 from any one workbook, seeded, so a rule that fires thousands of times is judged on the same footing as one that fires ten times.
- Each sampled finding is judged from a context card (formula, cached value, row labels, column header, a 5x5 neighbourhood, and the values inside and just outside the first referenced range). TP means the finding points at something a careful reviewer would want to look at for the reason the rule gives; FP means the rule misread the workbook; unsure means the card was not enough to tell.
- Precision is TP / (TP + FP) with a Wilson 95% interval. Small samples have wide intervals; read the interval, not the point estimate.
- This measures precision only. Recall needs ground truth; see the `euses-modified` source in `benchmarks/corpus/sources.json`.
- Forum workbooks are small and question-shaped, so volumes per 1k formulas will not transfer to large financial models; the per-rule precision is the more portable number.
